# Account information and deletion requests

Every verified account type can use **Profile → Settings → Account information and deletion**. These authenticated privacy controls do not grant marketplace/applicant admission and remain usable for one's own account while the public marketplace is closed. They do not depend on a paid plan or current business Terms acceptance.

The direct download is a ZIP containing `account.json`, a scope/readme file and eligible current documents. Account records include the user's profile, saved activity, own applications and their events, CVs, saved chats, notification preferences, verification submissions, billing references and privacy requests. Current owners also receive their business profiles/listings and eligible listing documents. A hiring account's copy never includes other candidates' application contents. Credentials, Auth/session and unsubscribe tokens, staff/security ledgers, protected backups, deleted files and provider-held records are excluded. Browser-only preferences stay on the device.

Downloads are assembled in server memory, delivered with private/no-store headers through an authenticated same-origin POST, and not placed in a public export bucket or emailed. A per-account database lease allows one successful download every 15 minutes; a failed attempt permits retry after a minute. Limits are 5,000 records per section, 8 MB of structured data, 250 unique current files and 64 MB of originals. The response is streamed to avoid the buffered function response limit. An oversized or unavailable original fails the whole archive; no truncated/partial success is returned. Users can request a complete information copy for larger accounts and additional records needing review.

Deletion and complete-copy requests appear under **Profile → Admin → Account privacy requests**. Only enabled administrators can review them. New requests produce private in-app administrator notices; responses produce a private in-app notice for the requester. No privacy contents are sent to an unverified address. Open requests can be withdrawn by the requester. Requests, responses and audit actions are stored privately, with optimistic concurrency checks to prevent stale reviews.

This queue deliberately does not execute erasure or billing changes. The requester asked for Admin-reviewed deletion. Before recording completion:

1. Verify the requester and requested scope. Review linked subscriptions, business ownership, shared records and any active hold.
2. Process an information copy or erasure through the controlled privacy procedure. Restrict an erasure to the correct account/records; never bulk-delete a shared business just because one team member leaves. Address ownership transfer and billing separately.
3. For actual Auth-account removal, revoke sessions before removal. Deleting an Auth user does not by itself guarantee immediate invalidation of every existing access token. Keep the protected owner/Admin access intact unless a separately authorised operator transition is complete.
4. Record the action taken and each retained record category, its purpose/legal basis and expiry or next review date in the response visible to the requester. Do not put unrelated third-party personal information or internal security details in that response. The existing policy's response target is 30 days; the queue records its due date and flags overdue requests.
5. Follow provider retention for backups and independently held records. Reapply deletion instructions after restoration. A billing obligation does not justify unrelated CV retention.

The Admin response's **Completed** state is an accountable record that the requested work was handled separately. It must not be used to imply that pressing the status button erased records. A request from an account subsequently removed remains linked to its request record, with the Auth user reference set null; retained request evidence still requires a documented purpose and retention review.

Business verification is separate. The applicant can withdraw a pending or information-needed verification application using **Verification → Withdraw verification application** and the confirmation dialog. The database locks/version-checks the request, records `withdrawn`, releases its pending capacity slot and writes a moderation audit. Approved/rejected applications cannot be withdrawn, a withdrawn request cannot later be approved from a stale queue, and review history is retained. The existing monthly submission-abuse limit still applies to later new submissions.

Launch Auth throughput was configured to 500 emails/hour on the Westmere Supabase production project. Existing 60-second per-user email interval, 30 sign-up/sign-in and verification requests per five minutes per IP, token-refresh limit and prelaunch admission gates remain. This is an initial launch ceiling, not a load-test guarantee; monitor legitimate traffic, shared server egress attribution, provider quotas and abuse before adjusting further.
